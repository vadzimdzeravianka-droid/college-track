# Ticket: Multi-User Support with Data Isolation

**Ticket ID**: T00000
**Status**: READY
**Priority**: HIGH
**Estimated Tokens**: 65K
**Groomed Requirement**: `.claude/workflows/requirements/groomed/support-different-students.md`

## Summary

Transform single-user passkey system to multi-user with data isolation. Add User model to database, update authentication to query users by passkey, and filter all college operations by userId. Enables multiple students to use the same deployment without seeing each other's data.

## Implementation Approach

**Approach A - Database-Stored Passkeys with Hashing**: Add User model with hashed passkey field (using bcrypt), update auth flow to query database and verify hashed passkey, add userId to College model with foreign key relation, filter all queries by userId from cookie. Include shell script to generate password hashes. Chosen for clean architecture, security best practices, and proper separation of concerns.

**Files**:

**Auth Helper Functions**:
```typescript
export async function getCurrentUserId(): Promise<string | null>
export async function requireAuth(): Promise<string>
export async function hashPasskey(passkey: string): Promise<string>
export async function verifyPasskey(passkey: string, hashedPasskey: string): Promise<boolean>
```

**Password Hashing**:
- Use bcrypt with salt rounds = 10
- hashPasskey wraps bcrypt.hash with pepper from PASSKEY_HASH_SECRET
- verifyPasskey wraps bcrypt.compare
- Never expose plain passkeys in logs or errors

**Login Flow Changes**:
1. Find user by hashed passkey in database (need to query all users or use email/username - see note below)
2. Verify passkey using bcrypt.compare against hashedPasskey
3. If verified, set two cookies: `user_id` (new) and `is_authorized` (backward compat)
4. Return success or 401 error

**Note on Login Query**: Since passkeys are hashed, we cannot query directly by passkey. Two approaches:
- **Approach A (Recommended)**: Query all users (acceptable for small user count <100), then bcrypt.compare each hash
- **Approach B (Future)**: Add username/email field to query by, then verify passkey hash

**Middleware Changes**:
1. Check for user_id cookie (primary)
2. Fallback to is_authorized for backward compatibility during transition
3. Redirect to /login if neither exists

## Edge Cases to Handle

- **Duplicate passkeys**: Database @unique constraint prevents duplicates
- **Empty passkey**: Validate passkey is non-empty in login
- **Missing userId in cookie**: Middleware redirects to login
- **Invalid userId in cookie**: requireAuth throws error, caught by error boundary
- **Existing colleges migration**: All existing colleges assigned to default user
- **Zero-downtime migration**: userId column nullable initially, then made required
- **Unauthorized access attempts**: Return 404 or error (don't leak existence)
- **Cookie security**: httpOnly, secure in production, sameSite=lax
- **Session expiry**: 30-day cookie (existing behavior preserved)
